## Introduction

You have inherited the Python backend of an LLM-serving app: 16 files, 2,454 lines – FastAPI layer, generation engine, model host, storage, and collector classes that hook into a transformer while it runs. Your job is to learn the codebase and start extending one of the modules.

All of that looks like a lot to learn and memorize. Code ReViewer offers an alternative to reading it top to bottom and building the map in your head. Right-click `backend/` folder, hit **Analyze with CRV**, and a second later every function becomes a graph node, coloured by one of the chosen metrics. That run – **2,454 lines in 1.0 s** – emits 245 lines of <Term>NDJSON</Term>: 14 metric descriptions, 33 modules, 78 functions, 19 extra definition locations, 101 call edges.

Code ReViewer is a VS Code / Cursor extension, built as our engineering thesis at Gdańsk University of Technology with [Gabriel Myszkier](https://github.com/gre-v-el) and [Jakub Stachowicz](https://github.com/jakubstachowicz). This project is After our defence in February 2027 it goes open source. For now, the extension is available in closed beta for interested parties, and documentation is live at [gre-v-el.github.io/crv-docs](https://gre-v-el.github.io/crv-docs/).

## Architectural Trade-offs: Name Matching Over Full Type Checking

Code ReViewer relies on **identifier matching** rather than full semantic analysis: there is no symbol table, type inference, or compilation step. 

Building a precise resolver is a major multi-year effort per language. To support three languages within the scope of a single thesis, we chose a heuristic approach. This trade-off allowed us to prioritize the visualization pipeline, metric calculations, and user interactions.

The parsing pipeline:

1. **Parse** each source file using <Term>ANTLR</Term> with community-maintained `.g4` grammars.
2. **Filter** the parse tree using per-language rule definitions.
3. **Traverse** the AST with a listener to extract modules, functions, and metrics.
4. **Collect** all call sites into an in-memory buffer without immediate resolution.
5. **Resolve** calls in a final pass after all files are parsed, matching valid calls to target definitions and generating graph edges.

### Filtering: throwing away most of the tree on purpose

An ANTLR tree is mostly ceremony – a single expression descends through a dozen precedence rules before reaching the identifier you care about. So we run a <Term>reduced parse tree</Term> pass first: each language declares a flat list of <Term>keep-rules</Term> (32 for C, 55 for Java, 33 for Python), anything else is deleted and its children spliced into its parent. Rules can be conditional – keep `postfixExpression`, but only when it holds a `(` (a call) rather than a `++`.


### Resolving: how a node and an edge get made

**Nodes come from definitions.** On entering a function-like construct the listener computes that subtree's metrics and calls `addFunction(name, uniqueName, metrics, startLine)`. The <Term>uniqueName</Term> is the key everything hangs off:

| Language | uniqueName | Consequence |
| --- | --- | --- |
| Java | `com.app.Repo.load` (package + type + method) | Overloads collapse into one node with several definitions |
| C | `opj_j2k_read_siz` (bare identifier) | Same-named statics in different files merge |
| Python | `collect` (bare identifier) | Every collector's `collect` merges |

A new key emits a node; a seen key appends a source location instead, which is why merged nodes show **Go to definition 1** and **2**. Modules are tracked with a *stack*, not "the last module I saw" – otherwise leaving a Python class attaches the next top-level function to the class you just left, and colours, contours and clustering all quietly lie.

**Edges come from call sites, but not yet.** A call site looks nothing up: it builds an ordered <Term>candidate list</Term> of names the callee might have and buffers it with the caller's key. In Java the list is genuinely inferred – receiver's declared type, then `this` type, superclass, interfaces, static imports – so the analyser tracks parameters and locals as `name → resolved type`. C and Python get a one-element list: the identifier itself.

**<Term>deferred call resolution</Term> is why it works.** Only after every file is walked does `flushCalls()` try each candidate against the map of all definitions:

```ts
for (const candidate of calleeUniqueNameCandidates) {
  callee = this.allFunctions.get(candidate);
  if (callee) break;              // first hit wins; later candidates are never tried
}

if (callee) {
  this.emit(call({ callerId: caller.id, calleeId: callee.id }));
}
```

Resolve at the call site instead and every forward reference and cross-file call vanishes.

### Silence as a design decision

A call to `torch.no_grad()` or `memcpy` produces no edge – and no node, no placeholder, no warning:

| Input | Lines | Call sites | Edges drawn | Resolved |
| --- | --- | --- | --- | --- |
| LLM-monitoring `backend/` (16 files) | 2,454 | 572 | 101 | 17.7% |
| `pybottle.py` | 4,583 | 1,310 | 506 | 38.6% |
| `j2k.c` | 13,180 | 1,616 | 149 | 9.2% |

The backend discards **471 of 572 call sites**, all into `torch`, `transformers`, `fastapi` or the standard library; drawing them would bury 78 real functions under hundreds of library leaves. So the graph shows what it can prove by name and stays quiet about the rest – **only ever as complete as the file set you hand it**, and an honest sparse picture beats a dishonest dense one.

## The metrics: what they are, and how we count them

### Cyclomatic complexity, and why it lives in the parse tree

McCabe's 1976 <Term>cyclomatic complexity</Term> counts the linearly independent paths through a function. Calculated formally as $E - N + 2P$ over its control-flow graph. For structured code it collapses to:

$$M = 1 + (\text{number of decision points})$$

A function with complexity 10 needs at least 10 test cases to cover every path. All the engineering is in determining *which* nodes count as a <Term>decision point</Term>:

```ts
calculateMetric(fn: ParserRuleContext): number {
  return 1 + countOccurrences(fn, this.decisionTokens, this.decisionRules);
}
```

`countOccurrences` counts two things: **terminal tokens** whose type is in one set, and **parser rules** whose index is in another. That split keeps the metric honest across languages instead of degenerating into keyword grepping:

- **Java** counts tokens: `if`, `for`, `while`, `do`, `case`, `&&`, `||`, `?`. Note the omissions – `else` and `default` add no path, they *are* the fall-through.
- **Python** counts `if`, `elif`, `for`, `while`, `and`, `or` as tokens, plus `except_clause` as a *rule*, since matching the token would also catch the `try`.
- **C** counts `case`, `&&`, `||`, `?` as tokens but takes `selectionStatement` and `iterationStatement` as *rules*: one `if … else` is a single node contributing exactly one decision – the right answer, and one a token-counter has to special-case its way to.

### Halstead: measuring a function as a vocabulary problem

<Term>Halstead metrics</Term> (1977) start from a different intuition: a program is a piece of language, so measure its vocabulary and length. Everything derives from four counts of <Term>operators and operands</Term> – $n_1$ distinct operators, $n_2$ distinct operands, $N_1$ and $N_2$ their totals.

We get them by classifying **token types** per language into two explicit sets, then running two counters over the tree: one sums hits, the other collects matched token *text* into a `Set`. Explicit sets rather than "everything that is not an operand" – grammars are full of tokens (`;`, `)`, `,`) that are neither, and counting punctuation as an operator inflates every number below.

From those four, eight <Term>composite metric</Term> values follow:

$$n = n_1 + n_2 \qquad N = N_1 + N_2 \qquad \hat{N} = n_1\log_2 n_1 + n_2\log_2 n_2$$

$$V = N\log_2 n \qquad D = \frac{n_1}{2}\cdot\frac{N_2}{n_2} \qquad E = D \cdot V \qquad T = \frac{E}{18} \qquad B = \frac{E^{2/3}}{3000}$$

**Volume** $V$ is information content in bits; **difficulty** $D$ rises when few operators are reused hard over few distinct operands; **effort** $E$ is their product, **time** $T$ divides it by Halstead's constant of 18 mental discriminations per second, and **bugs** $B$ is his defect estimate. For the two functions the walkthrough flagged:

| Metric | `_run` (`engine.py`) | `aggregate` (`benchmarks.py`) |
| --- | --- | --- |
| Lines of Code | 146 | 18 |
| Cyclomatic complexity | 18 | 11 |
| $n_1$ / $n_2$ | 7 / 136 | 8 / 26 |
| $N_1$ / $N_2$ | 76 / 342 | 17 / 65 |
| Volume | 2,993 | 417 |
| Difficulty | 8.80 | **10.00** |
| Effort | 26,341 | 4,172 |
| Time | 1,463 s (≈ 24 min) | 232 s |
| Bugs | 0.295 | 0.09 |

Read the columns against each other and the metrics stop being interchangeable. `_run` is eight times the size and seven times the volume; its 136 distinct operands say it touches a lot of things. `aggregate` is 18 lines and scores **higher difficulty**, working a handful of operators over a tiny operand set. Volume finds the big function, difficulty the hard one, and a reviewer watching line counts sees only one of the two. Do we believe `aggregate` holds 0.09 bugs? No – Halstead's constants were fitted to 1970s programs. The ordering *within one codebase* is the only claim the UI makes.

The eight derived values are not hardcoded in an order: each composite calculator declares its dependencies, and a Kahn topological sort at construction settles the sequence. That matters because the base calculator set is **per language** – if a future grammar cannot produce $n_2$, everything downstream drops out of the output automatically and the frontend never sees a metric it cannot trust.

## Every judgement call lives in the webview

The backend emits fourteen numbers and refuses to say which are bad. Ahead of them it emits a <Term>metric description</Term> per metric: name, hover text, and default thresholds (complexity good ≤ 10, bad ≥ 25; lines of code good ≤ 20, bad ≥ 50) – shipped as *data*, not baked into the values. The webview maps each raw value to a <Term>scaled value</Term> in 0…1, 1 at the good threshold and 0 at the bad one:

```ts
if (value <= good && low !== null) {
  return value <= low ? 0 : (value - low) / (good - low);
}
if (value >= good && high !== null) {
  return value >= high ? 0 : (high - value) / (high - good);
}
return 1;
```

Colour is one hue rotation over that score – `hsl(120 × score, 100%, 50%)`, red at 0, green at 1. Several metrics at once are combined by a join function you pick: **multiply** (one bad metric drags the node red) or **average** (a node must be broadly bad to look bad). Because the raw values already sit in the browser, dragging a threshold recolours the graph without touching the backend – re-running analysis to ask "what if complexity 15 is fine?" would make the question not worth asking.

### Rendering: surviving a thousand nodes in a webview

The graph tab is <Term>Sigma.js</Term> + graphology, and three decisions keep it usable.

**WebGL with a custom node program.** `@sigma/node-border` draws each node twice: an outer ring for module colour, a fill for metric colour – two facts, one glyph, no legend. Module hues are spaced by the golden angle (222.49°), so neighbours are never two shades of the same blue.

**<Term>ForceAtlas2</Term> in a worker.** LinLog mode, strong gravity, Barnes-Hut, off the main thread, auto-stopping after ten idle seconds.

**Clustering for free, via<Term>module anchor</Term>** No clustering pass: each module gets a hidden node and each function a hidden edge to it, so the layout pulls modules into blobs by itself and clicking an anchor zooms to its members. Contours on top are a custom fragment shader, switched off above 300 nodes where the blobs merge into one sheet.

Because the transport is <Term>NDJSON</Term>, nodes appear while analysis still runs: the host splits stdout on newlines, the webview switches on a one-character tag (`MD`, `M`, `F`, `L`, `C`) and mutates the graph in place. A repeated call thickens an existing edge instead of adding a parallel one, and that thickness feeds the layout as weight.

### Two engines, one wire format

Kotlin came first – ANTLR's home turf is the JVM. Then we wrote the analyser again in TypeScript, for one reason: deployment. A `.jar` needs `java` on `PATH`, a <Term>GraalVM native image</Term> is an unsigned binary, and managed corporate laptops block both – and a tool nobody at work may run has no users. The TypeScript backend is forked onto the Node runtime the extension host already runs under, so it needs nothing VS Code did not bring.

| `codereviewer.backend` | Artifact | Requires |
| --- | --- | --- |
| `node` (default) | `reviewer.js` | nothing |
| `jar` | `reviewer.jar` | `java` on PATH |
| `native` | `reviewer-<platform>` | a GraalVM build |

The unexpected benefit was verification. Two implementations sharing only the grammars and the protocol are a differential test of both: Kotlin regenerates golden NDJSON over shared fixtures, and the TypeScript suite asserts that every description, module, function, metric value, location and call edge matches – everything except emission order, which the webview treats as unordered anyway. Currently 123 tests across 20 files. Writing the engine twice is also how we found out the protocol was real: every disagreement marked a spec that had been living in one team's head.

### Where the graph stops being trustworthy

**Name collisions in C and Python.** 97 definitions became 78 nodes above, and the four collectors' `collect` methods are one vertex – an edge into it names the interface, not the implementation. Java escapes this only because its keys carry package and type.

**Dynamic dispatch.** Function pointers, `getattr`, runtime virtual calls – no name to key on, no edge. The graph under-reports exactly the code hardest to reason about.

**One language per selection.** Mix extensions and the backend refuses to run; cross-language calls do not exist in this model.

**Halstead's absolute numbers.** Ranking inside one codebase: useful. "This function contains 3.34 bugs": not a claim we make.

**Scale.** A few hundred nodes is comfortable, contours stop at 300, and a force layout over a monorepo is a hairball no colour rescues.

### What comes next

Three languages, fourteen metrics, one protocol, three backends – and the remaining work is additive. User-defined metrics come next: a metric is already a declarative description plus a calculator, so the work is exposing that seam. More grammars are close to free, which was the point of paying the ANTLR tax up front.
