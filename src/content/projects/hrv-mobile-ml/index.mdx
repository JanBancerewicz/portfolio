## Introduction & Core Problem

This project presents a research pipeline for real-time and offline analysis of heart rate variability (<Term>HRV</Term>) using non-invasive mobile sensors: a camera-based smartphone app (<Term>PPG</Term>) and a Polar H10 chest strap (<Term>ECG</Term>).

The core challenge in mobile <Term>HRV</Term> analysis lies in **beat timing accuracy**, not high-level classification metrics. Standard machine learning models often report high sample-level accuracy or classification <Term>F1</Term> scores for peak vs. non-peak frames, but frame-by-frame evaluation hides critical temporal errors.

In physiological monitoring, a detection is only valid if the predicted peak aligns with the actual heartbeat within a strict <Term>match tolerance</Term> window. Therefore, this project evaluates deep learning architectures (<Term>1D-CNN</Term>s) alongside classical baselines (<Term>Pan–Tompkins</Term>, <Term>NeuroKit2</Term>) strictly on beat-to-beat interval accuracy (<Term>RR interval</Term>s for <Term>ECG</Term> and <Term>IBI</Term> for <Term>PPG</Term>) rather than raw sample classification accuracy.

### What we built, with whom, on what data

This research project, developed at Gdańsk University of Technology (2025) and published in [TASK Quarterly](https://journal.mostwiedzy.pl/TASKQuarterly/article/view/3699) (March 2026), centers on an end-to-end Python ML pipeline ([research-project](https://github.com/JanBancerewicz/research-project)). It benchmarks custom <Term>1D-CNN</Term>s (featuring <Term>SE block</Term>s and <Term>LSTM</Term> layers) against classical algorithmic baselines (<Term>Pan–Tompkins</Term>, <Term>NeuroKit2</Term>) across dual-modality biosignals: Polar H10 chest-strap <Term>ECG</Term> and smartphone camera <Term>PPG</Term> (streamed via companion app: [PPGbetter](https://github.com/JanBancerewicz/PPGbetter)).

**ML & analysis stack:** Python 3, PyTorch (~2.6 CUDA), SciPy / NumPy / Pandas, NeuroKit2, scikit-learn, websockets. Pre-trained weights ship with the repo.

**Authors:** Jan Bancerewicz, Julian Kotłowski, Mateusz Rzęsa, Julia Morawska, and Ostap Lozovyy under the academic supervision of Ph.D. Julian Szymański.


**In scope:** ML architecture design and offline neural network training/evaluation, automated beat-matching logic within strict time tolerances, comparison against classical peak detectors, end-to-end signal filtering, <Term>HRV</Term> (<Term>RMSSD</Term>/<Term>SDNN</Term> from <Term>NN</Term> intervals) and <Term>PTT</Term> computation, and desktop GUI for live/replay signal inspection.

**Out of scope:** clinical certification, on-device mobile ML execution, full cohort raw dataset distribution (privacy/size constraints), production CI/CD, hospital integration.
## Why Standard Mobile Pulse Estimation Fails for HRV

Phone health APIs and raw brightness thresholds return a calm BPM curve. Research-grade <Term>HRV</Term> needs every beat timed on both modalities, then compared.

Camera <Term>PPG</Term> fights you in three concrete ways: the pulse can sit **inverted** (aligned PPG-vs-ECG validation multiplies the optical trace by `-1` before filtering), motion swamps the optical band, and the phone wall clock is not the Polar clock. Polar <Term>ECG</Term> at **FS ≈ 130 Hz** is the easier modality – but even there, “we trained a CNN” is meaningless unless you publish **<Term>match tolerance</Term>** and **label source**.

Without modality-specific <Term>band-pass</Term> filters, a refractory gap between accepted peaks, and an explicit classical or <Term>NeuroKit2</Term> reference, you cannot tell whether an <Term>RMSSD</Term> mismatch is physiology or a missed peak. That is the failure mode we designed against.

### Signal chain (same idea, different numbers)

1. **<Term>band-pass</Term>** – <Term>ECG</Term>: 5th-order Butterworth **0.5–45 Hz**. <Term>PPG</Term>: 4th-order **0.5–5 Hz**. Wrong passband quietly destroys peaks before any network runs.
2. **Classical peaks** – <Term>ECG</Term>: <Term>Pan–Tompkins</Term> (<Term>band-pass</Term> → derivative → square → integrate → threshold). <Term>PPG</Term>: local maxima with refractory spacing (~300–600 ms depending on the eval; comparison path often ~350 ms).
3. **Neural peaks**
   - **<Term>ECG</Term>** – input length **256**. Conv1D channels **1 → 16 → 32 → 64 → 128** (kernels 5 / 5 / 3 / 3), BatchNorm + LeakyReLU, max-pool, unidirectional <Term>LSTM</Term>, FC head → per-sample logits. Training: labels from <Term>Pan–Tompkins</Term> on filtered Polar recordings; BCE-with-logits; Adam **1e-4**. Two held-out recordings stay out of training.
   - **<Term>PPG</Term>** – segments **50–100** samples (paths disagree – real friction). Initial Conv1D 1→32 (k=7, GELU + BN); residual blocks 32→64 (k=9), 64→128 (k=5), 128→128 (k=3), 128→128 (k=7) with dropout; <Term>SE block</Term> on 128 channels; avg+max pool; FC → sigmoid per-sample peak probability. Validation uses a held-out multi-minute fingertip recording.
4. **Postprocess** – threshold probabilities (often 0.5; probabilistic <Term>PPG</Term> eval also uses height 0.25 on the probability trace), enforce minimum inter-peak distance, map to unix timestamps for pairing.
5. **<Term>HRV</Term> / <Term>PTT</Term>** – <Term>RR interval</Term> from <Term>ECG</Term>, <Term>IBI</Term> from <Term>PPG</Term> → treated as <Term>NN</Term> intervals → mean / <Term>SDNN</Term> / <Term>RMSSD</Term> (rolling window ~60 s in the paper narrative). After absolute-time alignment, pair each <Term>R-peak</Term> with the next chronological <Term>PPG</Term> peak:

```math
PTT = t_(PPG) - t_(ECG)
```

### Decisions worth defending

1. **Classical + neural side by side.** <Term>ECG</Term> training labels partly come from <Term>Pan–Tompkins</Term>. Shipping the classical detector next to the CNN makes label circularity visible instead of one glossy neural score.
2. **Separate architectures per sensor.** Polar <Term>QRS</Term> context at 130 Hz and camera pulse morphology are not one problem. Forcing a shared “universal beats model” would hide that.
3. **Thin phone, heavy desktop.** PPGbetter only acquires. Tkinter + CUDA/CPU PyTorch owns ML and paper figures. A plain <Term>WebSocket</Term> line protocol on :8765 stays trivial on Android – at the cost of no auth on `0.0.0.0`. Fine for a lab LAN.
4. **Explicit held-out recordings.** Not a full MLOps story, but an anti-leakage gesture that is written down rather than hoped for.

**Transferable rule:** publish <Term>match tolerance</Term> and label source next to every peak <Term>F1</Term>. Otherwise mobile-sensor results are not comparable across blogs or papers.

### What we would do differently next time

1. Improve the companion app before collecting data. We limited ourselves to a 30 Hz sample rate, which gives us a hard limit on how heart rate can be measured.
2. One shared eval config for sampling rate, window lengths, tolerances, and model paths.
3. Commit a frozen metrics snapshot from re-runnable comparison scripts.
4. Auth-bind the <Term>WebSocket</Term> to localhost or a token.
5. Smoke tests on synthetic sine / QRS fixtures.
6. Document **file replay** as the supported demo path; treat BLE + phone as optional.

We started with Polar <Term>R-peak</Term>s on a plot. We ended with a pipeline that can replay fingertip <Term>PPG</Term> beside Polar <Term>ECG</Term>, defend detector scores against classical and <Term>NeuroKit2</Term> references, and show side-by-side <Term>HRV</Term> without pretending sample accuracy is beat accuracy. Consumer sensors can support controlled <Term>HRV</Term> research. They do not forgive motion, clock skew, or optimistic metrics.
