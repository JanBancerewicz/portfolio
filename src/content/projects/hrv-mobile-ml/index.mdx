## Introduction & Core Problem

This project presents a research pipeline and desktop application for real-time and offline analysis of heart rate variability (<Term>HRV</Term>) using non-invasive mobile sensors: a camera-based smartphone app (<Term>PPG</Term>) and a Polar H10 chest strap (<Term>ECG</Term>).

The core challenge in mobile HRV analysis lies in **beat timing accuracy**, not high-level classification metrics. Standard machine learning models trained on biosignals often report high sample-level accuracy or classification <Term>F1</Term> scores (e.g. classifying individual signal frames as "peak" vs. "non-peak"). However, evaluating a model frame-by-frame hides critical temporal errors. In physiological monitoring, a detection is only useful if the predicted peak aligns with the actual heartbeat within a strict time window (e.g. <Term>match tolerance</Term> of a few milliseconds).

Miss a single peak or insert a false positive, and key HRV metrics like <Term>RMSSD</Term> (short-term variability) and <Term>SDNN</Term> (overall dispersion) become completely unreliable. Therefore, this project focuses on evaluating deep learning architectures (CNNs) alongside classical baselines (<Term>Pan–Tompkins</Term>, <Term>NeuroKit2</Term>) strictly on beat-to-beat interval accuracy (<Term>RR interval</Term>s for ECG and <Term>IBI</Term> for PPG) rather than raw sample classification accuracy.
### What we built, with whom, on what data

This research project, developed at Gdańsk University of Technology (2025) and published in [TASK Quarterly](https://journal.mostwiedzy.pl/TASKQuarterly/article/view/3699) (March 2026), centers on an end-to-end Python ML and evaluation pipeline ([research-project](https://github.com/JanBancerewicz/research-project)). The primary focus is benchmarking custom 1D Convolutional Neural Networks (featuring Squeeze-and-Excitation modules and LSTM layers) against classical algorithmic baselines (<Term>Pan–Tompkins</Term>, <Term>NeuroKit2</Term>) across dual-modality biosignals: Polar H10 chest-strap ECG and smartphone camera PPG (streamed via [PPGbetter](https://github.com/JanBancerewicz/PPGbetter)) - a companion app developed for this project.

**Six** subjects. **ML & analysis stack:** Python 3, PyTorch (~2.6 CUDA), SciPy / NumPy / Pandas, NeuroKit2, scikit-learn, Matplotlib, Tkinter, `websockets`, `bleak`. Pre-trained weights included in repo (`cnn/ecgcnn.pth`, `ppg_peak_model.pth`).

**Team:** Developed by Jan Bancerewicz, Julian Kotłowski, Mateusz Rzęsa, Julia Morawska, and Ostap Lozovyy under the academic supervision of Ph.D. Julian Szymański.


**In scope:** ML architecture design and offline neural network training/evaluation, automated beat-matching logic within strict time tolerances, comparison against classical peak detectors, end-to-end signal filtering, HRV (<Term>RMSSD</Term>/<Term>SDNN</Term>) and <Term>PTT</Term> computation, and desktop GUI for live/replay signal inspection.

**Out of scope:** clinical certification, on-device mobile ML execution, full cohort raw dataset distribution (privacy/size constraints), production CI/CD, hospital integration.
## Why Standard Mobile Pulse Estimation Fails for HRV

Phone health APIs and raw brightness thresholds return a calm BPM curve. Research-grade HRV needs every beat timed on both modalities, then compared.

Camera PPG fights you in three concrete ways: the pulse can sit **inverted** (aligned validation in `validate_ppg_vs_ecg.py` multiplies the signal by `-1` before filtering), motion swamps the optical band, and the phone wall clock is not the Polar clock. Polar ECG at **FS ≈ 130 Hz** is the easier modality – but even there, “we trained a CNN” is meaningless unless you publish **<Term>match tolerance</Term>** and **label source**.

Without modality-specific <Term>band-pass</Term> filters, a refractory gap between accepted peaks, and an explicit classical or <Term>NeuroKit2</Term> reference, you cannot tell whether an RMSSD mismatch is physiology or a missed peak. That is the failure mode we designed against.

## From camera capture app to side-by-side RMSSD

### How the system grew

**Start:** Polar BLE connect scripts and an early ECG CNN that plotted <Term>R-peak</Term>s – detect chest-strap beats, little else.

**Then (git arc):** live Tkinter plots → HRV GUI metrics → PPG CNN branch → timestamp/alignment fixes (`fix-hrv-final`, `peaks-compare`) → classical Pan–Tompkins baselines → redesigned PPG residual + SE network (`ppg: new cnn network`) → cleanup for publication.

**End:** Replay (or stream) fingertip PPG next to Polar/file ECG, mark peaks classically and with CNNs, show RMSSD / SDNN / RR side by side, export aligned CSV, reproduce detector comparisons. Under controlled recording, mobile PPG can approximate ECG-based HRV while staying more artifact-sensitive.

### Acquisition path

Entry point: `appgui/ngui.py` (“HR Monitor”). Two producer threads feed queues:

- **PPG** – `PpgData` listens on **`0.0.0.0:8765`**, protocol `timestamp value` (async <Term>WebSocket</Term>).
- **ECG** – `EcgDataBluetooth` (Polar) or `EcgDataFile` (CSV replay).

`ECGProcessor` (windows of **256** samples) and `PPGProcessor` (windows of **~100** samples) filter, detect peaks, and drive three tabs: **PPG + ECG**, **HRV** (RMSSD / SDNN / RR for EKG vs PPG), **Peaks Compare**. Save buttons write ECG, PPG, or both aligned; HRV plots export as PNG at 300 dpi.


Canonical happy path (replay or live):

```text
User -> ngui.py
     -> PpgData :8765  (async WS)  and/or CSV PPG
     -> EcgDataFile / BLE          (sync queue drain)
     -> ECGProcessor / PPGProcessor
           band-pass -> classical or neural peaks
           -> RR / IBI -> RMSSD / SDNN
           -> optional PTT on unix-aligned peaks
     -> Tkinter plots + optional aligned CSV
```

**Error paths that matter:** WebSocket disconnect freezes PPG while ECG may continue – dual HRV becomes meaningless until reconnect. Missing `.pth` triggers `get_or_train_model` (slow) or `find_peaks` fallback – under-detection, broken RMSSD. Science bottleneck is **cross-device time alignment**, not model FLOPs.

### Signal chain (same idea, different numbers)

1. **<Term>band-pass</Term>** – ECG: 5th-order Butterworth **0.5–45 Hz**. PPG: 4th-order **0.5–5 Hz**. Wrong passband quietly destroys peaks before any network runs.
2. **Classical peaks** – ECG: <Term>Pan–Tompkins</Term> in `pan_tompkins.py` (<Term>band-pass</Term> → derivative → square → integrate → threshold). PPG: local maxima / SciPy `find_peaks` with refractory spacing (~300–600 ms depending on script; comparison path often ~350 ms).
3. **Neural peaks**
   - **ECG (`ECG_CNN`)** – input length **256**. Conv1D channels **1 → 16 → 32 → 64 → 128** (kernels 5 / 5 / 3 / 3), BatchNorm + LeakyReLU, max-pool, unidirectional LSTM, FC head → per-sample logits. Training: labels from <Term>Pan–Tompkins</Term> on filtered Polar recordings; BCE-with-logits; Adam **1e-4**. Held-out files in `cnn/ecg/train.py`: `R20.csv`, `R21.csv`.
   - **PPG (`PPGPeakDetector`)** – segments **50–100** samples (paths disagree – real friction). Initial Conv1D 1→32 (k=7, GELU + BN); residual blocks 32→64 (k=9), 64→128 (k=5), 128→128 (k=3), 128→128 (k=7) with dropout; <Term>SE block</Term> on 128 channels; avg+max pool; FC → sigmoid per-sample peak probability. Validation holdout in `cnn/ppg/data.py`: `ppg_data_johnny_10min.csv`.
4. **Postprocess** – threshold probabilities (often 0.5; probabilistic PPG eval also uses height 0.25 on the probability trace), enforce minimum inter-peak distance, map to unix timestamps for pairing.
5. **HRV / PTT** – RR from ECG, IBI from PPG → mean / SDNN / RMSSD (rolling window ~60 s in the paper narrative). After absolute-time alignment, pair each <Term>R-peak</Term> with the next chronological PPG peak:

```text
PTT = t_PPG - t_ECG
```

Offline evaluation lives under `comparison/`:

| Script | What it answers |
| --- | --- |
| `ecg_ai_vs_pan_tompkins.py` | CNN vs <Term>Pan–Tompkins</Term> vs <Term>NeuroKit2</Term> on `data/ecg/ECG2.csv`; <Term>match tolerance</Term> ~**10 ms** (`0.01 * FS` at 130 Hz) |
| `ppg_ai_vs_real.py` | PPG CNN vs reference peaks on aligned CSV; tolerance often **150–250 ms** (ppg.md dump: **264 ms**) |
| `validate_ppg_vs_ecg.py` | PPG model vs ECG <Term>NeuroKit2</Term> peaks on aligned pair; invert + <Term>band-pass</Term>; `TOLERANCE_MS = 250` |
| `comparePPGECG.py` | Amplitude-aligned dual-trace visualization |

ECG and PPG <Term>F1</Term> numbers are **not directly comparable** until you normalize <Term>match tolerance</Term>. That is intentional honesty, not a bug in the write-up.

### Decisions worth defending

1. **Classical + neural side by side.** ECG training labels partly come from Pan–Tompkins. Keeping `pan_tompkins.py` and the comparison scripts makes label circularity visible instead of one glossy neural score.
2. **Separate architectures per sensor.** Polar QRS context at 130 Hz and camera pulse morphology are not one problem. Forcing a shared “universal beats model” would hide that.
3. **Thin phone, heavy desktop.** PPGbetter only acquires. Tkinter + CUDA/CPU PyTorch owns ML and paper figures. WebSocket `timestamp value` on :8765 stays trivial to implement on Android – at the cost of no auth on `0.0.0.0`. Fine for a lab LAN.
4. **Held-out file lists in training scripts.** `TEST_FILES` / `VAL_FILES` are not a full MLOps story, but they are an explicit anti-leakage gesture in a student research repo.

### What we would do differently next time

1. Improve the companion app before collecting data. We limited ourselves to 30Hz sample rate, which gievs us hard limit on how heart rate can be measured.
1. One `configs/eval.yaml` for FS, window lengths, tolerances, model paths.
2. Commit a frozen metrics JSON produced by re-runnable `comparison/` scripts.
3. Auth-bind WebSocket to localhost or a token.
4. pytest smoke on synthetic sine / QRS fixtures.
5. Document **file replay** as the supported demo path; treat BLE + phone as optional.
