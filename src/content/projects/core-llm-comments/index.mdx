## Introduction

Everyone has an opinion about whether comments help a language model write better code. Almost all of that opinion comes from reading the output and deciding whether it looks smarter. That measures prose, not reasoning.

**CORE** (COmments as a REasoning) asks the mechanistic version: given the same function with and without comments, does the model take a different internal route – or arrive the same way and only narrate differently? The planned intervention is an <Term>ablation</Term>: hold everything fixed, remove the model's ability to emit comments at decode time, and compare both generated programs and internal activations.

I am one of the authors on this workstream inside [Gradient PG](https://github.com/Gradient-PG), the AI/ML science club at Gdańsk University of Technology. The project is still in progress; we intend to publish a research paper and open the repository after the conference release. This write-up covers the engineering half that already works – not scientific conclusions, which we do not have yet. Applying the intervention turned out to be the easy part; proving the model would have done the thing you suppressed is still open.

## Why the intervention lives in the sampler

### Byte-identical prompts or nothing

A <Term>blocker pair</Term> must send byte-identical prompts, verified by hash. The pilot records confirm it – e.g. `HumanEval/0` at `00b2e074…557a`, 348 bytes, for both the allowed and blocked condition.

Appending "do not write comments" changes the prompt. Stripping comments after generation leaves activations already contaminated by the thing you meant to remove. The only place left is between the model and the sampler: a <Term>logits processor</Term> that, on every <Term>decode step</Term>, works out which vocabulary entries would extend the source into a comment and sets those logits to negative infinity before sampling.

## How the comment mask stays affordable

### Narrowing ~248k logits down to a few hundred

The honest check appends a candidate to the decoded context, re-parses with the language's <Term>comment extractor</Term>, and asks whether the appended region overlaps a comment span – the only way to get `#` inside a string and `//` inside `"http://…"` right. Running that over a ~248k logit row every step is arithmetically impossible, so the set narrows twice: once per vocabulary into <Term>opener candidate</Term>s filed under <Term>active trigger</Term>s, once per step to the groups the current context can arm.

On Qwen3.5-9B, Python has **761** <Term>opener candidate</Term>s (**197** always-live, **281** under `"`, **283** under `'`). Mid-function, only **197** of ~248k entries are classified – **0.08%**, in **7.7 ms**, of which **160** come back banned. Inside an open comment the narrowing inverts: ban by default, clear only verified <Term>closer candidate</Term>s (Python has **961**) plus special ids – otherwise EOS goes with the blanket ban and the request never stops.

### One parser, three languages so far

The same <Term>comment extractor</Term> package serves noise generation, post-generation span extraction, and the decode-time blocker. Java and C++ are already measured on the parser side – **1,308** <Term>opener candidate</Term>s each (**164** always-live + **1,144** under `/`) – waiting only on task families and per-request language plumbing to reach the runtime. Parser hot-path work also showed up in the numbers: skipping empty span scans cut Java from **98.3 → 89.2 ms/step** and Python from **210.3 → 190.3 ms/step** on a 162-candidate step against an 8.6k-character context.

## Silent failures cost more than slow ones

### The processor was accepted and then discarded

vLLM drops most processors when <Term>speculative decoding</Term> config is set. <Term>hidden-state extraction</Term> is implemented *as* a speculative method, so the flag was accepted by the request schema and the processor was thrown away before it saw a logit. The fix constructs the blocker explicitly in that branch. <Term>runtime diagnostics</Term> now ship invocation count, candidates examined, and tokens masked – because "requested" and "ran" had been the same claim for months and were not.

### Detection that failed without complaining

An unpaired apostrophe in prose (`don't`, chat templates, reasoning traces) made a fallback scanner swallow the rest of the buffer and hide every later `#` and triple quote. Decode context is prompt plus generation, so it is full of English – exactly where the real Python parsers bail out and the fallback scanners are the only detector left. Detection went to zero. The fix treats a literal left open by a newline as a stray quote, and the processor lexes only what follows the final closing think tag.

A third failure of the same species: `preprocess_vocab` used to have a <Term>fail-open default</Term> on the base class that returned every non-empty token. A <Term>comment extractor</Term> that forgot to override it did not crash – the candidate filter simply stopped filtering and the benchmark ran orders of magnitude longer. It is abstract now, so a missing filter fails at construction instead of at the end of a wasted night.

## What the pilot actually showed

### The mask fired; the bytes did not move

Qwen3.5-9B, temperature **0.0**, top_p **1.0**, seed **42**, 512-token cap, thinking disabled, eager decode. Five HumanEval tasks × two conditions (blocker OFF / ON). The run stalled later on a lock timeout – but `HumanEval/0` and `HumanEval/1` completed in both conditions with usable diagnostics.

`HumanEval/0` examined **50,987** candidates and masked **10,300** across **67** <Term>decode step</Term>s; `HumanEval/1` examined **19,025** and masked **3,568** across **25**. The paired completions were byte-identical under OFF and ON – same SHA-256. Not similar. The same bytes.

An earlier behavioral check had already found the same thing from the other direction: prompts that explicitly asked for inline comments still produced zero comments when unblocked, so the pre-registered validation threshold (≥ 2 comment-containing unblocked outputs) was unreachable. No criterion weakening, no output rewrite.

So the <Term>ablation</Term> is currently subtracting from zero. On this workload the model was not going to write comments; every masked logit was a token it was not going to sample. The blocker is correct, measured, and – here – inert. That is a workload problem, not an implementation one: we need tasks where the unblocked model reliably comments (longer tasks, chat mode, thinking enabled) before the blocked condition can differ.

## Status and what is still open

### Built, unfinished, and unclaimed

**296** CPU tests pass in **0.59 s**. The <Term>capture point</Term> for activations is verified against a pinned vLLM source fingerprint – a provenance guarantee, not a numerical tensor check. The <Term>ablation</Term> machine is built and instrumented.

<Term>EvalPlus</Term> is wired in (pinned to v0.3.1, prompts byte-verified against HumanEval+) and has never executed a generated program on this host, because Docker was unavailable. So there is not yet an answer to whether a model forbidden from writing comments writes worse code.

There is also no scientific conclusion yet on whether comments function as reasoning for the model. The paper is the planned deliverable; the repository stays private until that release. Until the workload produces comments to ablate, CORE's honest status is: intervention verified, experiment incomplete.
